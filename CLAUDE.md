## Stack
Next.js (App Router, TypeScript, Tailwind CSS v4), scaffolded via `create-next-app`. Navbar and Footer live in `src/app/layout.tsx` (shared across every page); `src/app/page.tsx` is just the homepage's section stack. Business facts (phone, email, service area, certifications) are centralized as placeholders in `src/lib/business.ts`, update that one file once real details are confirmed, rather than hunting through components.

**Supabase**: `src/lib/supabase.ts` exports a browser-safe client (`@supabase/supabase-js`) using `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` only. Put anywhere needing `SUPABASE_SERVICE_ROLE_KEY` (full DB access, bypasses RLS) in a separate server-only file, never this one, and never give it a `NEXT_PUBLIC_` prefix or Next.js will inline it into the browser bundle. Real credentials live in `.env.local` (gitignored, not committed), `.env.local.example` documents the shape with placeholders only and is safe to commit. `.gitignore` ignores `.env*` generally but explicitly un-ignores `.env.local.example`.

Real Supabase project (confirmed working 2026-09-16, verified live via a REST call): URL derived from the anon key's JWT `ref` claim as `https://<ref>.supabase.co`, double check this against Project Settings > API in the Supabase dashboard if anything seems off. Harri supplied the keys via a plaintext `Keys.txt` at the project root, migrated into `.env.local` then flagged for deletion since a plaintext secrets file sitting in the repo is a real risk once git is initialized. There was also a newer-format `sb_secret_...` key in that file with no named home in the 4 requested env vars, wasn't stored anywhere, ask Harri if he wants it kept (e.g. as a `SUPABASE_SECRET_KEY`) before it's lost for good.

`quote_requests` table (migration at `supabase/migrations/20260915104911_create_quote_requests.sql`; columns: id, created_at, name, email, phone, service, message, status default 'new') exists and is confirmed working end-to-end as of 2026-09-16, verified with a live insert through the real route plus a follow-up read via the service role key. Its RLS policy (anon INSERT-only) hit a real bug along the way, "new row violates row-level security policy" on every insert despite a seemingly-correct PERMISSIVE-looking setup, most likely the single policy having been created `RESTRICTIVE` rather than the default `PERMISSIVE` (a lone RESTRICTIVE policy denies everything regardless of its own check, since there's then no PERMISSIVE policy to grant access in the first place). **This is now moot**: writes no longer go through the anon key or that policy at all (see below), so it no longer blocks anything, but if RLS is ever revisited, check `permissive` in `pg_policies`, not just `with_check`.

Cross-page nav links use `/#section-id` (via `next/link`, not a plain `<a>`, or the lint rule fails) so they work from `/privacy` too, not just the homepage. Same-page anchors within `Hero.tsx`/`OurWork.tsx` (which only render on the homepage) stay as plain `#section-id`.

**Quote request flow, rebuilt 2026-09-16**: the contact form (`src/components/ContactForm.tsx`) no longer talks to Supabase at all, client-side. It POSTs `{name, email, phone, service, message}` to `src/app/api/quote-request/route.ts`, which does the insert server-side via `src/lib/supabase-admin.ts` (a lazily-constructed client using `SUPABASE_SERVICE_ROLE_KEY`, bypasses RLS entirely by design, never import this into a Client Component) and then, on successful insert, best-effort emails a notification via Resend. A failed or unconfigured Resend send never fails the request back to the customer, the row is already saved, it just `console.error`s. There is no more `src/lib/supabase.ts` (anon client) or `src/app/api/notify-quote/route.ts`, both deleted as dead code once this replaced them. `location` and the out-of-area distance warning still aren't their own columns, they're folded into `message` as a prefixed note. The service `<select>` options are generated from `coreServices` in `business.ts` rather than hardcoded, keep it that way so they can't drift out of sync with the real service list again (they previously did, silently, for a while).

**Notification recipient, superseded 2026-09-16**: `NOTIFY_TO` and `FROM_ADDRESS` in `route.ts` briefly used the interim `harri.davies05@gmail.com` / `onboarding@resend.dev` pair while `proservelectrical.co.uk` was unbought and unverified in Resend. That domain is now bought, verified, and aliased, see the Deployment section for the current, correct state (`Proservchester@sky.com` / `quotes@proservelectrical.co.uk`). Leaving this history here only as a reminder of why those interim addresses existed, don't revert to them.

When verifying Resend behavior, prefer their `GET /emails` API (`Authorization: Bearer <RESEND_API_KEY>`) over trusting a 200 from the app's own route, a rejected send still returns `{"ok":true}` to the client by design (graceful degradation), so the app's response can't tell you whether the email actually went out, only Resend's own log can.

**Mobile audit, 2026-09-16**: checked all 3 pages across 6+ phone widths (300 to 430px) for horizontal overflow and console errors, none found on any page content. The one real gap was `Navbar.tsx` itself: the nav links (`Services`, `Why Us`, `Service Area`, `Contact`) were `hidden sm:flex`, meaning phones had zero way to reach them except scrolling, no mobile menu existed at all. Fixed with a hamburger (`lucide-react`'s `Menu`/`X`) that expands a dropdown panel via `AnimatePresence`, closes on link click or on resize past the `sm` breakpoint. While building it, found and fixed a second, narrower bug: at exactly 320px (a real, common width, iPhone SE 1st gen and several older/small Android phones) the header's own content was ~10px wider than the viewport, clipping the hamburger button's right edge. Root cause was cumulative: `px-6` container padding, `gap-3` between logo and nav groups, and the full-size logo chip/wordmark/quote-button all sized for desktop with no mobile-specific trim. Fixed with `sm:` responsive overrides (smaller padding, gaps, logo chip, wordmark, and quote button on mobile, all restored to original desktop sizing at the `sm` breakpoint), verified back down to 0px overflow at widths as low as 300px. If touching `Navbar.tsx` again, re-run this check, it's an easy regression to reintroduce by adding anything to the header row without checking it against 320px specifically, most "mobile-friendly" testing defaults to 375px+ and would miss it.

**Notification email design, 2026-09-16**: the notification email is now on-theme HTML (dark green header bar, amber "NEW QUOTE REQUEST" badge, green field labels) with a plain-text fallback, built by `src/lib/quoteEmailHtml.ts`. A matching branded PDF copy of the request is generated with `@react-pdf/renderer` (`src/lib/quotePdf.tsx`, `generateQuotePdf()`, white background rather than the site's dark theme, deliberately, a print/PDF-viewer document reads better light, ink-heavy dark backgrounds don't) and attached as base64 via Resend's `attachments`. Both templates escape user input (`escapeHtml` in `quoteEmailHtml.ts`) since name/email/phone/service/message are all customer-supplied and get interpolated into HTML. When checking these templates render correctly, add a temporary route under `src/app/api/` that calls `generateQuotePdf`/`buildQuoteEmailHtml` and returns the result directly (`application/pdf` or `text/html`), screenshot or fetch it, then delete the route, don't leave debug routes lying around. One gotcha hit doing this: a route folder name starting with `_` (e.g. `_debug-pdf`) is a Next.js "private folder" convention and gets silently excluded from routing, giving a 404 with no other explanation, avoid leading underscores for anything meant to be reachable.

The form asks for a job location and geocodes it on blur (via `src/lib/geo.ts`'s `geocode()`, hitting OSM Nominatim client-side) to flag jobs outside the 25-mile service radius. It doesn't block submission, just warns and points the visitor to email. If enquiry volume grows, move the geocoding behind a server route with caching rather than hitting Nominatim directly from every visitor's browser.

**React gotcha hit here**: in an async form handler, `event.currentTarget` becomes `null` after the first `await` (React nulls it once the synchronous part of the handler finishes). Capture it into a local variable (`const form = event.currentTarget`) before any `await`, not after. Getting this wrong made a successful submission silently render the error state, since `form.reset()` threw and the catch block overwrote the "success" status that had just been set.

`/privacy` page exists with placeholder copy only, flagged inline as needing real legal review before launch (UK GDPR/PECR).

Animations use `motion` (Framer Motion). `src/components/Reveal.tsx` is the shared scroll-reveal wrapper, use it for new sections rather than hand-rolling `whileInView` each time. Hero and Our Work are fullscreen (`min-h-screen` / `h-screen`) sections with parallax background photos via `useScroll`/`useTransform`. `src/components/Sparks.tsx` renders the rising amber spark-trail ambient effect (Harri's request, "add trails"); pass `density` to scale it down for a section.

Navbar is `fixed` and transparent over the Hero, turning solid black/glassy on scroll (tracked via a `scrollY > 60` listener in `Navbar.tsx`). Sections with anchor ids (`#services`, `#why-us`, `#service-area`, `#contact`) use `scroll-mt-20` so the fixed nav doesn't cover them when jumped to.

Service area map (`src/components/ServiceAreaMap.tsx`) uses `leaflet` + `react-leaflet` with plain OpenStreetMap raster tiles (free, no API key). CartoDB's dark tiles were tried first but now require a key and show an "API KEY REQUIRED" watermark without one, don't reach for those. The map needs `ssr: false` in `next/dynamic`, which Next.js's App Router only allows from a Client Component, hence the `"use client"` wrapper in `ServiceAreaMapLoader.tsx` rather than calling `dynamic()` straight from the (server) `ServiceArea.tsx`.

Both are shown in `Navbar.tsx` inside a white rounded chip, since they carry their own white background rather than being transparent. `src/app/icon.png` (the favicon) was generated from `logo-icon.png` the same way, padded onto a white square.
